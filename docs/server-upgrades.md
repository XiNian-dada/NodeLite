# Server 升级与失败恢复

安装器把一次升级绑定到具体 release，并校验该 release 的二进制、配置模块和升级模块摘要。
候选程序必须能通过 `--version` 报告目标版本，并以只读的 `upgrade-manifest` 子命令解析配置；
下载、摘要或配置预检失败时不会替换当前程序或改写当前配置。同一安装器的并发运行由文件锁拒绝。
Linux 运行环境需要 `flock`、GNU `timeout`、`realpath`、`tar`、`curl` 和 systemd。

## 提交升级的条件

1. 停止现有服务，确认其进程已经退出。
2. 备份原程序、systemd unit、配置、节点注册表、快照、GeoIP 数据及历史/审计 SQLite 文件。
   数据库备份包括 `-wal`、`-shm`、`-journal`，并记录升级前不存在的文件。
   相对路径按原服务的 `WorkingDirectory` 解析，配置目录外的数据库也包含在内。
3. 补齐配置默认项，以同目录临时文件原子替换配置和程序，再启动新服务。
4. 直接探测配置监听地址的 `/readyz`，要求 HTTP 200、`X-NodeLite-Version` 等于目标版本，
   并且连续两次探测成功时 systemd 的 `MainPID` 相同，才打印升级成功。

就绪等待默认 60 秒，`NODELITE_SERVER_READY_TIMEOUT_SECS` 可设为 2–300 秒。
每次网络请求和 systemd 命令还有各自的短超时。通配监听地址会转换为回环地址，探测绕过代理。
该检查确认版本和流量就绪；`/readyz` 的非阻断诊断仍应按[探针语义](readiness.md)持续观察。

## 失败行为与备份

启动即退出、持续不就绪、版本不符或中断都会使安装器非零退出，不会打印成功。
新程序已经启动过时，恢复流程先停服并验证全部备份摘要，再恢复所有兼容数据及原来不存在的文件状态，
最后恢复原程序和 unit。只有数据恢复全部成功，才允许重新启动先前运行中的旧服务；
升级前未运行的服务在恢复后保持停止。已有服务的开机启用状态保持不变。
旧 release 没有版本响应头时，恢复检查只要求 HTTP 200 和稳定的服务进程。

如果备份损坏、文件恢复失败或无法确认停服，安装器报告恢复未完成，不会尝试启动旧程序。
管理员应先确认服务停止，再修复或恢复完整的兼容数据，不能只把旧可执行文件放回去后启动。
恢复到升级前快照会丢弃新程序验证窗口内接收的数据或配置修改。
进程被强制杀死或主机掉电无法触发 shell 的自动恢复；保留的备份用于人工恢复。

备份保留在原安装目录的 `.upgrade-backups/upgrade.*`，安装器输出具体路径。
目录权限为 `0700`，文件为 `0600`，其中包含凭证与监控数据。每次升级都保留完整备份，
管理员确认升级稳定后可按自己的保留策略清理，并应为升级预留足够磁盘空间。

备份中的 `status` 记录是否已提交或回滚；`N.path` 给出原文件的绝对路径，`N.tar` 保存该文件及元数据，
`N.absent` 表示升级前不存在、恢复时必须移除的文件。恢复顺序为数据和配置在先，程序与 unit 在后。
在备份目录中可核验完整性：

```sh
sha256sum -c checksums.sha256
sha256sum -c checksums
```

CI 使用真实 SQLite WAL 和 HTTP 服务注入启动失败、503、版本错误、迁移失败、备份损坏、恢复失败和信号中断；
Linux CI 还通过独立的临时 systemd unit 重复关键场景，不操作运行中的 NodeLite 服务。
